## 2. Establish the horizon and criteria conversationally

- If the number of dates `N` is absent, ask for it as one question. If the start date is absent, inspect the Pacific-date editorial calendar and existing scheduled/published/draft horizon; default to the next unfilled future stretch, **never overwriting existing records silently**. State the exact date range before generating. If the phrase “next N days” would include already scheduled dates, explain the coverage and choose the first N unfilled consecutive dates only when that is clearly consistent with intent; otherwise ask one precise clarification. Avoid unnecessary repeated questions.
- Before generating, establish the editorial criteria. Ask **one** criteria question: “Same criteria as last time, or different?” unless the owner already specified the recipe. “Same” means the most recent explicitly owner-approved recipe, not an assistant guess. If the exact latest recipe is not visible in the current request, ask the owner to restate the recipe **before generating**, rather than assuming the dated example below remains current. This follow-up replaces, rather than adds to, the initial criteria question when the owner has already said “same.” Label the agreed recipe as an editorial preference, not a shipped generator contract.
- **Historical example, not an automatic default — editorial recipe agreed November 12, 2026:** a recognizable 1970s/1980s backbone, with a mix of 2000–2025 players—generally 1–3-time All-Stars—in the later slots; recognizable/easier names early, moderate difficulty in the middle, deeper but fair challenges late; some diversity of era, teams, roles, and positions. This is an *editorial preference*, not a hard automatic eligibility guarantee. If the owner changes it, reflect the new criteria for that batch. Do not claim precise All-Star counts or player recognition grades without verified data.
- **Existing portable slot-rank contract (authoritative):** slots 1–2 ranks 1–250; 3–4 ranks 251–1,000; 5–6 ranks 1,001–2,500; 7–9 ranks 2,501–5,000. Never silently replace domain rank rules with the editorial preference. Distinguish an owner-approved manual out-of-band exception from automatically eligible generated selections.

## 3. Generate and validate privately

1. Resolve every chosen player through the existing canonical resolver; require a single, approved, reveal-ready identity. Do not guess ambiguities or use display-name equality as identity proof. Automatic picks come from the ranked `dailyEligiblePlayers` stream; manual authorized picks can be outside it, with the existing warning.
2. Use the production Daily algorithm and reviewed data version as the baseline, but recognize that its rank/seeded-hash path does **not** implement owner-specific era or All-Star criteria. Where verified player-source facts support approved criteria, apply those criteria when selecting/replacing candidates **without changing their original recognizability ranks or authorized slot bands**; rerun the canonical validator on the resulting ordered nine. If the criteria cannot be applied with verified data, say so explicitly and request the owner's approval for a transparent fallback **before** presenting proposals as satisfying the recipe. Generate dates sequentially with actual history and already-proposed selections. All lineups must have nine ordered slots, nine canonical-unique players per date, and no duplicated player across the proposed batch by default.
3. **Automatic 90-day no-repeat:** exclude any canonical player with a sourced Daily occurrence **1–90 calendar days before or after** the proposed date; 91 days is eligible. Check earlier published/archived lineups, confirmed scheduled bookings **including future dates after the proposal**, relevant earlier proposed batch dates, and any applicable official edition—not only the primary. Compare the actual Pacific calendar-day gap, not a UTC timestamp or the order candidates were generated. Treat unconfirmed drafts as reservations requiring disclosure/review, not proof of played lineups. Reconstructed deterministic fallback lineups may be used as conservative repeat candidates but must be labeled **unverified** where original served rosters cannot be proved (#589). Include all other proposed batch dates bidirectionally before saving; never change a later booked lineup without the owner's explicit instruction. Fail visibly if trustworthy usage coverage is insufficient; never silently widen the repeat window or player pool.
4. Apply the current validator: canonical identity, reveal readiness/hint completeness, **unchanged source rank-band fit**, exact slot order, both earlier and later 90-day booked usage, and automatic-pool status. Where an editorial preference (e.g. 1–3 All-Star selections) lacks approved data, mark it unverified and obtain approval for the proposed deviation before claiming the final selections meet that preference; do not invent facts or elevate player stats into editorial recognizability evidence.
5. Give a readable day-by-day nine-player lineup with slot order, dates/puzzle numbers, and useful flagged exceptions. Show an aggregate repeat check and any coverage gaps. These are private owner-facing previews, not public GitHub payloads.

## 4. Manual substitutions and last-use reporting

For **every** owner-proposed replacement (even if it appears safe):

- Resolve the exact canonical identity, and read the current target lineup/revision before changing anything. Check duplicates in that lineup, every proposed batch date, and verified past/later booked official editions with an absolute 1–90 Pacific-calendar-day gap; report future conflicts even when the candidate date comes first.
- Search **all supported official Daily usage sources** and distinguish **verified published/archived roster records** from scheduled bookings, unconfirmed drafts, and reconstructed deterministic fallback candidates. An occurrence supported only by reconstructed deterministic history is **reconstructed, not verified**: the original served roster may differ (#589). Report each sourced date/status and its evidence class, the latest verifiable past roster occurrence and any **later booked** occurrence within 90 days of the proposed date; include absolute calendar-day gaps. Drafts and scheduled records do not prove the public played that player.
- If a prior use is within 90 days, clearly warn with the exact previous date and day gap. The owner may explicitly override for a **manual** pick; do not override automatically or silently change the requested player. An unknown, ambiguous, or non-reveal-ready identity remains blocked regardless of the owner's repeat exception.
- If there is no match, say **“No prior use found in the records checked”** and describe the coverage; say “never used” only when all applicable historical sources have been reconciled and support that conclusion. Report missing historical rows and source gaps as uncertainty, not as zero usage.
- When a repeat or rank warning exists, propose a few genuinely eligible alternatives if useful, but make no substitutions without owner approval. Confirm the updated nine-player uniqueness and batch-wide 90-day checks after each edit.

## 5. Save, schedule, verify

- **Generate/review** and **save draft** and **schedule** and **publish** are distinct lifecycle steps. Do not mutate anything merely because the owner asked for proposals. Save through the **existing authorized private ChatOps/application editorial workflow** with `schedule: false` only after the owner wants drafts persisted. Do not directly `UPDATE`/`INSERT` production `daily_editorial_puzzles` through SQL or circumvent revision-CAS, authorization, audit, or server validation.
- Scheduling requires explicit owner instruction such as “schedule these” or the established editorial usage “publish these for their assigned dates.” For future puzzles this means schedule them for their respective dates, **not reveal/publish future answers immediately**. If the user explicitly requests immediate future publication, distinguish that from normal scheduling and do not do it through an unsupported path. Published/archived records remain immutable.
- Before dispatch, confirm date, exact ordered nine canonical IDs, uniqueness, current status/revision, and disposition of warnings. Never automatically replace a previously scheduled lineup or reset active gameplay; require specific owner approval for such changes. Use only a transport independently cleared for private roster and credential confidentiality (#666); never queue new future lineups or reusable authorization credentials in an unapproved shared database transport. If the authorized transport is unavailable, stop **before saving or scheduling**, preserve the private reviewed proposal, and explain the blocked operational step rather than using direct SQL. Once cleared, require `schedule: true` for approved future scheduling.
- After each dispatch, inspect the private HTTP response and authoritative persisted row for exact identity, slot order, revision, actor/status, and schedule metadata. A request ID, apparent HTTP success, or transport timeout alone does **not** prove completion. On timeout, read back **before** any retry. Check all dates; explicitly separate completed, failed, and blocked dates.
- Do not take a scheduled record's `published_at: null` as a failure of scheduling. Do not call scheduling publication, production release verification, or hosting QA if only scheduling completed.

Provide (a) date range and number of lineups, (b) criteria used, (c) repeats avoided / accepted manual overrides and last-use dates, (d) draft/scheduled/published status by date after authoritative verification, and (e) anything needing owner attention. Keep the response concise and private.
