# Browser review repair roadmap

Status: R1–R4 implemented; browser review prerequisites are repaired and comparison may resume as separate bounded concerns.

Preserve engine scoring, immutable transport/storage contracts, separate populations and Classic compatibility. All repairs are web-owned. No new runtime dependency, schema, lease, forced takeover or anti-cheat authority.

## Ordered PR scope contracts

1. **R1 delivery lifetime — implemented.** A released owner cannot start another retry or mutate a journal acknowledgment. Delivery now uses a disposable exact attempt/generation owner session; the persistence hook disposes it synchronously before releasing the Web Lock. Late success/error is locally inert, pending exact payloads remain for successor retry, and takeover/interleaved-append regressions cover the original counterexample. No retry scheduling, gameplay request, schema or persistence-mechanism change.
2. **R2 gameplay requests — implemented.** Reset/restore plus persistence-session teardown and owner-loss transitions invalidate every old Guess/Give Up callback through a small synchronous single-flight request-generation controller in the web layer. Success, error and settled callbacks run only for the current generation; stale cleanup cannot clear a newer pending request. The persistence hook only signals request-authority invalidation; it does not own request UI or scoring. The existing shared Daily/Classic resolve path, request payloads and scoring behavior are unchanged.
3. **R3 persistence authorization — implemented.** Web Lock authority and analytics eligibility are now separate. A tab that acquires the lock but cannot safely fence the journal keeps exclusive gameplay ownership with contribution disabled; journal recovery does not re-enable contribution until a later ownership acquisition. Durable reload failure retains the lock while exposing a non-writable blocked state, and unexpected lock-request failure is also non-writable. Only explicit missing Web Locks/abort capability retains the pre-existing non-contributing compatibility persistence path. Deterministic regressions cover corrupt journals with two tabs, generation-write failure plus later recovery, reload failure/takeover, degraded-owner completion eligibility, and the exact writable-access set. No Classic ownership, schema, storage-format, lease, scoring or server change.
4. **R4 re-bootstrap authorization — implemented.** Persistence setup now keys off semantic puzzle/date/number/ruleset identity rather than object or bootstrap-token identity. True session changes reset readiness and expose checking/follower state until durable restoration and current authority agree. Save and reset both require the render's session/access/readiness to match the live session/access/readiness refs, so a stale owner render cannot write after cleanup/re-bootstrap. Missing owner refs fail closed instead of performing an untracked save. Deterministic regressions reproduce the stale-owner predicate and exact-session/readiness requirements. A mounted React DOM harness was not added because no such test dependency exists and the scope contract explicitly stops before adding one; preview/production browser verification remains the integration check. No scoring, Classic ownership, schema, storage format, lease or server-authority change.
5. **R5 delivery recovery.** Goal: finite network requests and bounded owner-scoped retry opportunities. In scope: AB browser transport/scheduler and focused tests. Retry on meaningful events, no polling/tight loop, no historical scan. Out: comparison recovery and infrastructure. Acceptance: failure followed by online/new-terminal opportunity, no duplicate concurrent requests, cleanup cancellation.
6. **R6 save decoding.** Goal: malformed saves return unusable without crashing or creating inferred observations. In scope: storage decoder boundary and fault regressions. Out: compatibility policy, storage schema, completion backfill. Acceptance: malformed nested structures and unchanged supported saves.

R7 modularity is addressed within its owning behavior: request controller, authority/readiness boundary, dedicated delivery scheduling. R8 request admission/observability stays a separate follow-up; do not invent rate-limit infrastructure or silently strengthen anonymous authority. Record concrete acceptance criteria before implementation.
