## Confirmed product requirements

1. On the hitter reveal, show the current supported batting columns in the same relative order as the supplied Baseball-Reference screenshot: `AB, R, H, HR, RBI, SB, BA, OBP, SLG, OPS`. Do not add screenshot columns without supported facts. Keep career and season tables consistent. Pitching order was not specified by the hitter screenshot; preserve the current pitcher display unless a separate decision changes it.
2. Hint 4 should include pitcher saves (`SV`) when supported and present its stats in the same relative order as the corresponding full reveal. Never invent a save count for a hitter, an unavailable pitcher, or a two-way player's missing pitching line.
3. Daily Nine's proposed new outcome scoring: HR `4`, triple `3`, double `2`, single `1`, walk `0`, strikeout/Give Up `-1`. Wrong guesses do not deduct points on their own; the third wrong guess remains a strikeout. Nine at-bats give a possible total from `-9` to `36`. These are **new versioned rules**, not a reinterpretation of `points-v3` or a resurrection of historical `points-v2`. The owner explicitly accepts negative scores. Future `walk = 0.5, strikeout = 0` remains a possible *later* version, with its own result and comparison population; do not introduce fractional storage until that rule is chosen.
4. Show the mode-appropriate “How to play” dialog automatically on each game-page entry/reload, including the new scoring explanation on Daily Nine. Dismissing it once does not suppress it on later visits. Retain a visible way to reopen it. The dialog must not open again on unrelated React rerenders or interfere with saved-game hydration, focus, keyboard use, or mobile play.
5. A terminal generational suffix (`Jr`, `Sr`, including periods/case) contributes no initial: `Ken Griffey Jr.` -> `KG`, `Tony Gwynn Sr.` -> `TG`. Preserve the player's actual display name, identity, search/aliases, and meaningful interior tokens (`De La Cruz`, hyphens, ordinary middle names). Test edge cases rather than stripping arbitrary trailing words or `II`/`III` without a product decision.

## Verified seams and implications

- **September 24 clarification:** archived puzzles use the currently active public scoring rules for each newly started play. Issued lineup/clue facts are frozen, but scoring is not permanently tied to issuance. Keep any earlier-version play under its original ruleset; a later replay with new rules uses a separate browser save and result population. An archive comparison must bind the permanent puzzle ID and the exact ruleset of the played attempt, never all results for the same date. Old scores are not recalculated. Browser save isolation scope: `tasks/plans/archive-browser-save-isolation.md`.

- The canonical reveal uses `apps/web/app/revealPresentationConfig.ts` and structured reveal facts; career and season tables share its column list. Daily hint 4 currently uses `Player.statsLine` through `buildDefaultDailyHints`, not those reveal columns. `DEFAULT_ALPHA_SETTINGS.statsHintConfig` lists `bwar`, but the current generated `statsLine` deliberately has no WAR and the canonical reveal does not populate WAR. Treat the listed bWAR configuration as a legacy mismatch, not evidence of available WAR. The canonical data feasibility docs still mark WAR unsupported. Do not scrape or fabricate Baseball-Reference facts. Prefer a shared typed display-order policy and formatting from existing structured, provenance-backed facts; never parse a display string as the data source. Check current player coverage before changing hint output, including two-way players and missing stats. The source/data prerequisite is split into `tasks/plans/pitcher-saves-data-contract.md`: sourced save zeroes remain zero while unavailable career save totals stay absent. Changing what hint 4 reveals changes puzzle difficulty, so avoid an untracked mid-puzzle change.
- `generateInitials` lives in `packages/engine`; `createPlayerIdentity` in `apps/web/app/dailyPuzzleAdapters.ts` applies it to current editorial puzzles. Existing signed gameplay uses the resulting public initials, and result validation compares submitted initials to the authoritative puzzle. Permanent schema-v2 snapshots now freeze ordered canonical player IDs plus rendered initials and hint text; archive v2 materialization uses those stored clues. Schema-v1 compatibility remains readable, and the production issued table is still empty. PR review found that a day-boundary-only rollout would change older beta puzzle initials on replay and reject delayed submissions. The owner approved historical compatibility: beta editorial/fallback and schema-v1 archive puzzles before September 28, 2026 retain the legacy initials; puzzles from that date onward omit terminal Jr./Sr. The date-aware code must be deployed before that Pacific day begins or the cutover moves forward. Scope: `tasks/plans/terminal-generational-suffix-initials.md`.
- The present Daily Nine implementation is explicitly `points-v3` across shared types, engine, completed/at-bat result validation, immutable browser attempt journal and outbox, comparison API and client, SQL constraints/RPCs, score histogram `0..63`, scorecard, share, and how-to text. The old `points-v2` table has `4/3/2/1/0.5/0`, but that is a historical ruleset and not a safe live alias. New `-1` terminal outcomes require signed score bounds in database and portable comparison validation and a histogram indexed by an offset (`score - minimumScore`), not a negative array index. Do not relax the existing `points-v3` range check for its rows. Keep raw facts and server-derived awarded points authoritative; keep comparison reads asynchronous and noncritical. Beating a finisher remains strictly lower score, including negatives; ties remain ties. Do not add rollup tables or cache to support this change.
- Today's generic save key is date-based and its non-Classic compatibility rule accepts other points rulesets. Classic uses a storage namespace wrapper. Session and owner-lock keys already contain puzzle ID/date/ruleset in some paths, while saved-game, journal, delivery, and reset paths do not all share one archive identity policy. The archive PR must trace **all** of these. Ruleset changes also must not load a prior `points-v3` save as the new current rules; preserve old beta data without silently converting or resubmitting it.
- The archive runtime is a server-only composition. No public archive route, history surface, or launch epoch has been configured. Preserve its fail-closed behavior for unissued dates and its existing token identity checks.

## Reversibility and launch checks

- A later 0.5/0 policy gets a *new* ruleset version. Retain v4 rows and ability to interpret/share them. Re-evaluate numeric or scaled-half-point storage and histogram step in that PR. Never recompute old awarded points using the new policy or merge the populations by date alone.
- A clue-format change cannot silently alter an already-issued permanent puzzle. Keep canonical IDs as answers and freeze the needed versioned clue representation or materialized clue data before issuance. Test old/new clue versions and response redaction at the same time.
- Before public archive exposure: verify no beta history was imported, no launch epoch set, no permanent row fabricated, current Daily and Classic save paths intact, archive paths isolated, and the table remains append-only/service-role-only.
- Before each PR merge: fresh-eye architectural review, focused checks, full required CI/data pipeline/build, exact-head Preview, documentation gate, Supabase read-only/schema checks where relevant; then verify merge SHA, push CI when available, production READY and error/fatal logs, open PR state, and relevant hosted table posture. If a CI event is absent, report it precisely rather than claiming a pass.
